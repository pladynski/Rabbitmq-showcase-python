# A RabbitMQ-based service interaction boilerplate

### Purpose.

Develop a clear and intuitive boilerplate that provides a foundation for building scalable and reliable applications using a message-broker–driven architecture (RabbitMQ), ensuring it is accessible and practical for widespread use.

### Description

This template contains three main directories: `api`, `service1`, and `service2`. The `api` directory handles incoming client (frontend) requests and distributes them to the appropriate services using RabbitMQ as the message broker. The services always consume incoming messages and process them.

### RabbitMQ-driven architecture is beneficial when:

1. **Scalability Needs**: When your application must handle significant and fluctuating loads, asynchronous messaging lets individual components scale independently.

2. **Complexity Management**: For applications that benefit from decoupled components, message queues help break the system into manageable, independent services, simplifying development and maintenance.

3. **Fault Isolation and Resilience**: Broker-based communication enhances fault tolerance by isolating failures to individual services and smoothing spikes in traffic.

Use message-broker architecture when these factors align with your project’s requirements, but be aware of the trade-offs, such as increased complexity in deployment, monitoring, and inter-service communication patterns.

### Theoretical usage

It is assumed that all your services will be placed in separate Git repositories. Ensure that all components have access to the necessary environment variables, which can be managed using Docker and Kubernetes. This template uses RabbitMQ as the message broker, so you need to know how RabbitMQ works (different types of exchanging, exchangers, queues, routing keys), but you can also consider alternatives like Apache Kafka or even the HTTP protocol.

### Local usage

To better understand message-broker-driven architecture, launch each Docker container in separate terminal windows and explore their interactions:

`docker-compose -f docker-compose.message-broker.yml up`
`docker-compose -f docker-compose.api.yml up`
`docker-compose -f docker-compose.services.yml up`

Next, go to `localhost:8000/docs` and send requests to any of the routes. Observe the logs generated by the service containers to see how they handle the requests.

## Graftcode version

This fork shows the same boilerplate with the **api → service1 / service2 RabbitMQ hops replaced by [Graftcode](https://www.graftcode.com)**.
The topology is unchanged: `api` (FastAPI, port 8000), `service1` and `service2` are still three separate Python processes.
`service1` and `service2` are each hosted by **Graftcode Gateway (`gg`)** on their own port (8101 and 8102).
`api` calls them through **grafts**: the PyPI packages `graft-pypi-notify-service` and `graft-pypi-balance-service`, which `gg` generated from each service's public method.
The caller has no broker connection, exchange, queue bind or publish. Each endpoint makes one typed method call to the remote service.

### What changed

| Side | File | Change |
| --- | --- | --- |
| Producer (`service1`) | `service1/graft/notify_graft.py` (new) | Public `NotifyService.notify_user(payload_json: str) -> bool`. It passes the same JSON body that used to be published to the `notify_user` queue to the **unchanged** `logic.notify_user` handler. |
| Producer (`service2`) | `service2/graft/balance_graft.py` (new) | Public `BalanceService.change_balance(payload_json: str) -> bool`. It runs the **unchanged** async `logic.change_balance` handler on the same JSON body. No broker message needs acking, so `message.process()` is a no-op context. |
| Producers | `service*/graft/pyproject.toml`, `service*/run-graft-server.sh` (new) | Module definitions for `gg`. Each script runs `gg --runtime python --modules ./graft/` (service1: `--port 8101`; service2: `--port 8102`). |
| Consumer (`api`) | `api/main.py` | `publish_to_rabbitmq(...)` / `await a_publish_to_rabbitmq(...)` replaced by `NotifyService.notify_user(json.dumps(data))` / `await run_in_threadpool(BalanceService.change_balance, json.dumps(data))`. The routes, payloads and responses are the same. |
| Consumer | `api/config.py` | `first_service_graft_host` / `second_service_graft_host` (`ws://localhost:8101/ws`, `ws://localhost:8102/ws`). They can be overridden through env vars (`FIRST_SERVICE_GRAFT_HOST`, ...), like the other `pydantic-settings` values. |
| Repo | `.gitignore` | Ignores the `gg` runtime cache `.graftcode/`. |

Not changed: `service1/logic.py`, `service2/logic.py`, `service*/main.py` + `service*/broker.py` (the original RabbitMQ consumers still work, see smoke test part D), `api/broker.py` (no longer imported by `api`), Dockerfiles and docker-compose files.

**Behavioural differences:**
- With RabbitMQ, the API returns as soon as the message is published, even if the service is down, and the message waits in the queue. With the graft, the API returns after the remote call has finished. If the service node is down, the call fails and the endpoint returns HTTP 500. Nothing is buffered. If you need that kind of durability, keep the broker for that flow.
- Upstream `service1` uses `basic_consume` without acking, so its messages stay unacknowledged and are redelivered every time it reconnects (we measured `notify_user 1 1` after one request). With the graft, each call runs the handler exactly once.

### How to run it locally (tested with gg 1.5.1, CPython 3.12.16, FastAPI 0.165, uvicorn 0.54)

```bash
pip install fastapi uvicorn pydantic-settings pika aio-pika   # aio-pika/pika: needed by the services' logic.py imports

# gg: curl -fsSL grft.dev/get/gg | sh
# 1) service1 and service2, each hosted by Graftcode Gateway in its own process
./service1/run-graft-server.sh      # ws://localhost:8101/ws
./service2/run-graft-server.sh      # ws://localhost:8102/ws
#    If gg cannot find libpython, set HYPERTUBE_PYTHON_RUNTIME_PATH=/path/to/libpython3.12.so
#    and PYTHONPATH=<your site-packages>.

# 2) Install the generated grafts. Copy the exact commands each gg prints
#    (also at http://localhost:8101/pypi and http://localhost:8102/pypi), e.g.
#    pip install --extra-index-url https://grft.dev/simple/<GUID>__free graft-pypi-notify-service==1.0.0
#    pip install --extra-index-url https://grft.dev/simple/<GUID>__free graft-pypi-balance-service==1.0.0
#    (Without --projectKey the <GUID> changes on every gg restart. An installed graft keeps working
#    across restarts as long as the public methods stay the same.)

# 3) api (third process, port 8000) calls the services through the grafts
cd api && python main.py

curl -H 'Content-Type: application/json' -d '{"id":50,"user_id":12}' localhost:8000/api/user/subscribe
# -> {"detail":"User subscribed."}; the service1 gg process logs: [*] - User with id 12 just notified. And subscribed
curl -H 'Content-Type: application/json' -d '{"id":50,"user_id":12}' localhost:8000/api/order/checkout
# -> {"detail":"Order created."}; the service2 gg process logs: [*] - User's balance with id 12 changed. Order checkouted
```

The Docker/compose files were not changed or tested for the Graftcode path. They still describe the original RabbitMQ setup.
